What the plan gets right
✓ StrongServer-side shredding is architecturally correct — browser never receives data it shouldn't see. This directly addresses the Jane Street/Optiver network-tab threat model.
✓ StrongFirebase Custom Claims as the tier signal is the right call. Claims are cryptographically signed by Google — impossible to spoof via local storage or cookie tampering.
✓ StrongAES-256-GCM envelope encryption with Cloud KMS protects sensitive PII (phone, email, salary, interview notes) even from rogue internal engineers with Firestore console access.
✓ StrongSingle source of truth in Firestore with DENY ALL client-side rules. No fragmented tables = no synchronisation drift between tier-specific databases.
✓ GoodConcierge onboarding via Google Apps Script → Next.js → Firebase Admin is a clean, manual-but-automatable flow suitable for a small high-ticket client base.
Gaps to address before launch
CriticalNo audit logging. You need a record of every /api/candidates call — who requested it, which tier, how many records were returned, timestamp. Without this you cannot detect data exfiltration or honour DSAR/GDPR requests. Add Cloud Logging or Firestore audit trails.
CriticalNo rate limiting on /api/candidates. A Diamond client could script 10,000 requests and harvest the full dataset in seconds. Add per-firm request throttling (e.g. 100 req/hr) at the API gateway or Next.js middleware level.
ImportantTLS/HTTPS is assumed but not specified. The document doesn't explicitly mandate HTTPS, HSTS headers, or certificate pinning. State this clearly and enforce HSTS with at least a 1-year max-age in Next.js middleware headers.
ImportantToken revocation on tier downgrade. Firebase JWTs have a 1-hour TTL. If a firm's tier is downgraded, they still have Diamond access for up to 60 minutes. Add a server-side revocation check (Firestore flag + cache invalidation) for downgrade events.
ImportantDEK rotation strategy missing. The plan generates a unique DEK per document but doesn't specify how often DEKs are rotated or what happens when the KEK is rotated in Cloud KMS. Document a re-encryption job.
ConsiderCandidate consent and data residency. You're storing phone numbers, personal emails, and salary expectations of real candidates. Confirm data residency (India? EU? US?) and that candidates have consented to this storage and sharing — especially for GDPR-adjacent firms like those in London.
Verdict: move forward — with two fixes first
The core architecture is sound and production-ready for a v1 launch. Before onboarding real firms, add audit logging and per-firm rate limiting — both are low-effort additions to Next.js middleware. The remaining gaps are important but can be addressed iteratively post-launch.
